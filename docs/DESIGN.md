# 設計文書: NotebookLMスライド → 編集可能PPTX 変換パイプライン v2

## 背景と診断結果 (2026-08-19)

### 入力の実態
- NotebookLM (Gemini) のスライドは **1376×768 のラスタ画像** として生成される。
- 検証に使ったPDFは PowerPoint 2021 から書き出されたもので、各ページは
  「NotebookLM画像1枚(全面) + ユーザーがPowerPoint上で追加したテキスト/小画像」の構造。
- 画像内の文字は描画済み(焼き込み)。小さい文字はAI生成特有の崩れ(疑似漢字)を含む。

### 旧パイプライン(v1)の問題点
1. **フォント不一致が根因の精度不足**: 画像内の欧文は強いコンデンス体 (実測 w/h=20.0)。
   Arial Narrow でも +36% 幅過大。日本語も詰め組み(実測でどのフォントでも +25〜31% 幅過大)。
   → 字間・サイズを画像から解いて合わせる仕組みがなく、112要素の手調整が必要だった。
2. **OCRの断片化と誤読**: PaddleOCR 2.x + タイル分割で単語が分断・重複・誤読。
3. **200dpiレンダリングによる無駄な拡大**: 元画像は1376×768。3556×2000へ拡大してから
   処理しており、ぼけた画像でOCRしていた。
4. **PDFオーバーレイの無視**: PowerPoint追加分のテキストは正確な情報(フォント・サイズ・色)が
   PDFに残っているのに、画像化してインペイントしていた。
5. **手調整の成果物(build_text_layout.py)が資料固有**: 別資料に転用できない。

## v2 アーキテクチャ

### 原則
- **決定論**: 生成AIによる手調整・推測を排除。全て計測とコードで解く。
  (OCRと修復モデルはローカル推論のみ。ネットワーク・クラウド不要)
- **スケール**: 100ページ級に対応。ページ毎キャッシュ+レジューム、逐次処理でメモリ一定。
- **資料非依存**: 資料固有の座標・補正をコードに書かない。

### パイプライン (ページ単位)
```
acquire → ocr → measure → solve → group → remove → compose → qa
```

1. **acquire** (`pages.py`)
   - PDF: ページが「全面1枚画像」なら埋め込み画像をネイティブ解像度で抽出。
     PDFテキストspan(フォント・サイズ・色が正確)と小さなオーバーレイ画像も取得。
     それ以外のページは高解像度レンダリング。
   - 画像ディレクトリ/複数画像も入力可。
2. **ocr** (`ocr.py`)
   - RapidOCR (onnxruntime) + PP-OCRv6 japan small。2×Lanczos拡大で認識。
   - 行単位の検出。信頼度を保持し、低信頼行は review レポートへ。
3. **measure** (`inkstats.py`)
   - 各行のタイトなインクマスク(局所Otsu)から: インクbbox、色(メディアン)、
     縦グラデーション(上下1/3の色差)、ストローク幅(距離変換)。
4. **solve** (`solver.py`) — 精度の核
   - 候補フォント(インストール済み+同梱)で同テキストをPILレンダリングし、
     インク形状を照合して: フォント、サイズ(pt)、字間(spc)、太字、位置を解く。
   - サイズ: render ink高さとの比で決定。幅: 字間spcで一致させる。
   - 位置: インクbbox整合 + フォントメトリクス(hhea/OS2)でPowerPointの行高計算を再現し、
     テキストボックスの座標に変換。
5. **group** (`lines.py`)
   - 同スタイル・等間隔の行を段落グループ化(行間は spcPts で正確に指定)。
   - 整列検出(左/中央/右)でアンカーを決め、編集時の挙動を自然に。
6. **remove** (`removal.py`)
   - 領域ごとに背景を分類: フラット/緩勾配 → 決定論フィル(高速・完全)。
     複雑背景(写真・グロー) → LaMa (IOPaint、ローカル推論)。LaMa無効時は
     古典インペイントにフォールバック(品質低下を許容)。
7. **compose** (`pptx_writer.py`)
   - 16:9 (または元アスペクト) スライド。背景=ネイティブ解像度画像。
   - PDF由来オーバーレイ画像は個別ピクチャとして再配置。
   - テキスト: a:latin + a:ea、spc、正確な行間(spcPts)、グラデーション文字(gradFill)、
     グロー/シャドウ、オートフィット無効。
8. **qa** (`qa.py`)
   - 自前レンダラ(同じフォントメトリクスでPIL描画)で合成画像を作り、元画像とSSIM/差分。
   - ページ毎スコア+低信頼OCR行を `report.json` / コンタクトシートに出力。
   - macOSではKeynote経由のPPTXレンダリング検証も可能(オプション)。

### 実測に基づく決定
| 論点 | 決定 | 根拠(実測) |
|---|---|---|
| OCR | RapidOCR PP-OCRv6 japan small | 行単位で完全検出・誤読大幅減・約2秒/ページ(CPU) |
| 作業解像度 | ネイティブ画像(1376×768)基準、OCRのみ2×拡大 | 200dpi再レンダリングは劣化コピー |
| テキスト除去 | 適応式(フラット=決定論フィル / 複雑=LaMa) | 古典手法はグロー帯で破綻、LaMaはクリーン |
| 幅合わせ | 字間spc必須 | 全フォントで+25〜36%幅過大 |
| スライドサイズ | 16:9へ微伸長(<1%) | 1376:768=1.7917 vs 16:9=1.7778 |

### スケール対応 (100ページ)
- `work/pages/NNN/` にページ毎の中間物 (source.png, ocr.json, layout.json, removed.png)。
- マニフェスト(入力ハッシュ+パラメータ)で不変ページをスキップ(レジューム)。
- OCR/計測/解決: 約2〜5秒/ページ。LaMaはMPS/CUDAで数秒〜十数秒/ページ、
  必要領域のみに限定して実行。
- メモリ: 常に1ページ分のみ保持。

### 行レイアウトの較正結果 (tools/calibrate.py, Keynoteレンダラ実測)
- 通常行送り(lnSpc未指定)はレンダラ依存が大きい:
  CoreText系はtypo/hheaメトリクス、GDI系はusWin*を使い、
  Noto Sans JPでは最初のベースライン位置が最大0.28em(32ptで約13px)ずれる。
- **全段落でa:spcPts(行高固定)を指定**すると、ベースライン = 行高 − ディセント
  で安定し、実測誤差は全ケース±3px以内 (1376px幅キャンバス基準)。
- よってpptx_writerは単一行にも常にspcPtsを設定する。

### フォントの可視性
- `fonts/` のフォントはPPTXレンダラ(PowerPoint/Keynote)からは見えない。
  `fetch_fonts.py --install` でユーザーフォントとしてインストールする。
- macOSはインストール直後にフォントデーモンのキャッシュが残るため
  `killall fontd` が必要な場合がある。

### 外部調査で確定した事項 (2026-08)
- **NotebookLM純正PPTXエクスポート**: 2026年2月から公式対応(PDFに加えPPTX)。
  ただしAIがレイアウトを再生成する方式で、アプリ内で見た画像と同じ見た目にはならない
  (フォント置換・レイアウト差異の報告多数)。**「見たままの再現」には本ツールが必要**。
  Google Slidesエクスポートは「coming next」のまま未リリース。
- **PP-OCRv6は50言語統一モデル**(japan専用モデルは存在せず、lang_type指定は無視される)。
  small=日本語88.2% / medium=90.5%(自己申告)。tinyは日本語非対応。
  モデル・コードともApache-2.0で商用利用・同梱再配布可。
  オフライン運用はDet/Rec.model_pathで明示パス指定が確実(既定は初回に
  site-packages配下へ自動DL。読み取り専用環境では失敗する既知問題)。
- **kern属性は「カーニングを有効にする最小フォントサイズ」**(量ではない)。
  "0"の意味は曖昧なため、無効化には大きい値(kern="10000")を書く。
- **LibreOfficeのPPTXテキストレイアウトは1.2em固定モデル**(実コード確認済み)で、
  PowerPointのフォントメトリクス依存レイアウトとは一致しない。
  LOレンダは幅・フォント解決の検証には有効だが、縦位置の最終検証は
  実PowerPointでのキャリブレーション(プローブpptx→PDF→PyMuPDF実測)が正。
- **フォント埋め込みはEOT形式必須**(生TTF不可、CFF系OTF不可)。Noto Sans JPの
  SubsetOTFはCFFのため埋め込み不可 → 現方針は「受け渡し先でのフォントインストール」。
  埋め込み対応(fontTools instancer→pyftsubset→EOT化)は将来課題。
- spc(字間)は1/100pt絶対値、±4000ptまで負値可。末尾グリフ後にも加算されるかは
  未文書化のため、中央揃え+大きな負spcでは±spc/2のずれが理論上あり得る(要実測)。

### 精度チューニングの一般則 (2026-08-20確定、全て資料非依存)

2資料(金色×ダーク調 / コード風ライト調)の実測反復で確定した規則。
数値は `config.py` に集約されている。

| 規則 | 値・内容 | 防いでいる事故 |
|---|---|---|
| テンプレート照合(NCC) | 認識テキストを候補フォントで実描画し `matchTemplate(TM_CCOEFF_NORMED)`。サイズは初期推定の0.70〜1.12倍を1px刻み | 二値化ベースのサイズ解決がグロー・JPEG劣化でぶれる |
| 照合の許容変位 | インク**中心**基準で縦±0.18em・横±0.28em | 隣接行へのマッチジャンプ(重なり)。上端基準だとグローで窓外れ |
| サイズ上限プライア | em > OCR検出枠高×0.95 にペナルティ | リング・グロー上の小テキストの過大解 |
| ウェイト候補 | スコア上位6+未登場ウェイト帯(細/中/太)の最良を必ず照合 | 太字が候補落ちして細字が誤選択される |
| 小文字の太字抑制 | インク高<20pxでは僅差時に軽いウェイトを優先 | JPEGでストロークが太めに測れて過剰bold(滲み) |
| 字間の可読性下限 | spc ≥ −0.08em (幅一致より可読性を優先) | 詰めすぎで文字が重なり潰れる |
| 純色サンプリング | 背景から最遠の上位30%画素のチャネル別メディアン | 縁の混色で白が灰色にくすむ |
| グロー付与条件 | ハロー輝度 > 背景+25 かつ コア高≥16px | 暗色遷移帯への光彩誤付与(文字が濁る) |
| スクリプト判定 | 和文文字が25%超のときのみ和文候補 | 全角記号1文字で等幅・コンデンス候補を失う |
| NFKC正規化 | 欧文主体の行のみ適用(全角記号→ASCII) | OCR由来の全角コロン等が未収録グリフ化 |
| スペース復元 | ギャップ外れ値 + **画像上の空白列の実在検証** | 検出ボックスの偽ギャップによる誤スペース |
| 混在サイズ分割 | 強調数字ランのみ(高さ1.3倍+両端に段差1.2倍) | 単語途中での誤分割 |
| 隠しテキスト抑制 | 不透明カバー(持ち越し画像・塗り図形)に6割以上覆われた行は復元も除去もしない | 原本で覆い隠されていた焼き込み文字の蘇生 |
| Z順序 | 背景→復元テキスト→オーバーレイ画像→オーバーレイテキスト→ネイティブ図形 | 復元テキストが持ち越し要素の上に浮く |
| 照合領域は縦横とも確保 | 探索領域は最大テンプレート寸法を下限に縦横拡張 | テンプレートが領域より広く照合が全スキップされる |
| 幅由来のサイズ下限 | 探索下限を「インク幅÷送り幅」の幅適合サイズまで拡張 | 隣接行のインク混入で高さ由来の初期推定が膨張し真のサイズに届かない |
| 照合全滅時の安全弁 | 検出枠高×0.88でサイズをクランプ+要確認フラグ | 素の過大推定のまま出力され巨大文字が重なる |
| 混在行のプール統合 | 和文文字を1つでも含む行は和文候補も土俵に乗せる | かな非搭載の欧文フォントが選ばれサイズ崩壊・はみ出し |
| 装飾テキストの保持 | 相関<0.15かつ(枠高比>2.0 or 信頼度<0.8)の行は画像のまま | アーチ状・変形文字を巨大な直線テキストとして「蘇生」 |
| 丸記号の字形確定 | 丸様文字のみの行はグリフ輪郭の入れ子を実測し ◎/○/● へ置換 | ◎をOと誤認し欧文フォントの巨大な「OOO」になる |
| 幾何記号もプール統合 | ◎○●※等を含む行は和文候補も土俵に乗せる | 記号非搭載の欧文フォントで豆腐化・字形崩れ |
| 極性リトライ | NCC<0.35なら逆極性(明暗反転)で計測し直しNCCが良い方を採用 | 明るい帯上の白文字でバーの影を「暗い文字」と誤計測 |
| 正字間の自然字間裁定 | 字間>+0.11emの解は自然字間テンプレートも並行照合しNCCに裁定させる | バー端・グローの混入でインク幅が膨張し文字が間延び |
| 非和文境界のスペース復元 | 欧文語・×等の境界もギャップ(0.24em超)+空白列検証でスペース復元 | 「Human Capital」「A × B」のスペース消失 |
| レイアウト検証スペース復元 | camelCase・記号・和欧境界の予測位置に空白列が実在し、挿入でNCCが改善する場合のみスペース挿入 | 単語ボックスが融合した「CareerPotential」等のスペース消失 |
| 行端の紛らわしい字形裁定 | 行頭・行末の混同字(ヘ/〜等)は代替字テンプレートとNCC比較で確定 | 装飾の波ダッシュ「〜」がカタカナ「ヘ」として出力される |
| 色ラン分割 | 文字セルごとの純色を計測し、輝度正規化クロマ距離+輝度比の切り替わりで色ランに分割(書式は共有) | 行内の部分強調(金色・赤色)が1行1色に潰れる |
| 非段落の分解 | 行送り>1.6em・短いデータセル列(<4.5em)・整列残差大の縦並びは個別ボックスへ | 表の行・注釈列が1ボックスに融合し編集時に道連れ、位置も累積ズレ |
| 実測行間の追従 | 段落内の行間は一律ピッチでなく実測ベースライン間隔を段落ごとにspcPts指定 | 中央値ピッチの一律適用で下の行ほど位置がずれる |
| 冗長パッチ図形の解消 | 焼き込みテキストと同内容の不透明テキスト図形は落とし、焼き込み側を復元。ただし落とした後も他カバーに4割超隠れる場合は「再レイアウト」なので保持 | 編集不能への手当てパッチが二重表示を起こす/落とすと断片だけが露出する |
| テーマの持ち越し(PPTX入力) | 入力のtheme1.xml(配色・フォントスキーム)を出力へコピー。生成テキストは全て実値指定なので影響なし | schemeClr・テーマフォント参照のネイティブ図形が入力と違う色・折り返しになる |
| LaMaのチャンク実行 | 12ページごとに修復結果を書き戻して完了記録(中断しても続きから再開) | 長時間バッチが中断(OOM等)すると全修復が失われる |
| ページ内サイズ調和 | 実測インク高が近い行をクラスタ化し、NCC≥0.6の行が3行以上支持するサイズへスナップ(2アンカー以上は最寄りへ=意図的な2段サイズを保護) | 同格の箇条書き・注釈のサイズが計測揺れでバラバラになる |
| 面(フォント)の調和 | 色サブグループ(白本文と金注釈を混ぜない)ごとにNCC≥0.55の多数決フォントへ統一 | 同格アイテムの太さ・書体が行ごとにバラバラになる |
| 列内左端スナップ | 左端が近い(±0.6em)3行以上の原点を中央値へ(±0.35em以内のみ) | 個別ボックス化した列の左端が数pxずつ波打つ |
| 調和の幅サニティ | 調和の再解決は「行送り幅≤インク幅×1.12+1.2em」を満たす場合のみ採用 | 誤スナップで長文行が伸びてスライド外へはみ出す |
| 発光整合 | グローのハローが本体色より輝度+60超明るい場合は明極性で再計測(物理的整合を優先、NCCは粗い門番) | 発光文字が暗色で解決され「薄く」見える |
| 調和のNCCガード | サイズスナップの再解決も照合が大きく劣化(0.8倍未満かつ0.30未満)する場合は棄却 | 劣化した解が画像保持判定をすり抜けて崩れたまま出力される |
| 最終判定への一本化 | 画像保持(NCC<0.22)の判定と除去マスクの確定を調和・統一の後に実施 | 後段で劣化した行が「除去だけされて」背景に穴が残る |
| 行端の未認識インク検査 | 検出枠のすぐ外に本文と同色調のインクが残る行をreviewへ記録(隣接検出行がある側は除外) | 「(一般社団法人…」の「(一」等の取りこぼしに編集時まで気づけない |
| 変形疑いの裁定 | is_warpedは疑いフラグに格下げし、直線テンプレートで相関≥0.5が出る行は再構成(出ない行のみ画像保持) | 背景ノイズの誤検知で直線テキスト約70行が不必要に画像化・編集不能 |
| 小テキストの幾何検証つき受理 | 高信頼(≥0.97)・小サイズ(em≤30px)・幅/サイズ整合の行はNCC 0.15まで受理 | 写真背景上の小文字が相関希釈で画像のままになり編集できない |
| 資料全体のフォント調和 | script別の多数派フォント族(NCC≥0.5の行の投票)へ外れ行を再照合して統一。劣化ガード・幅サニティ・等幅保護つき | 同じ役割の本文がページごとに近縁の別族へ割れて資料全体で不統一 |
| 異体字・簡体字の正規化 | OCRが返す簡体字・旧字体(约200字)を日本標準字体へ無条件写像 | 认证・體驗・專など50言語統一OCR由来の異字体が残る |
| 辞書検証つき形近字修復 | 壊れ=OOVまたは「1文字漢字断片の隣接連続」。置換は壊れ形態素内の漢字→漢字のみ、採用は行品質の厳密改善+置換位置を含む形態素が2字以上の漢字辞書語(人名(姓)は棄却)になる場合のみ | 「改州」「機閔」等の誤読が残る/助数詞「300人」・送り仮名語幹「見据えた」・人名稀少語「八的」への誤修正 |
| ネイティブ文字化け修正 | 持ち越しネイティブ図形のa:tにも同じ修正を適用(段落連結→1対1置換→同位置書き戻し。ランを跨ぐ語も対応) | ラウンドトリップ入力(以前の出力への加筆)に残る化け字が直らない |
| ネイティブスライドの素通し | 全面画像の無いスライドは変換対象外としてそのまま持ち越す(画像はオーバーレイ再配置) | 加筆・差し替えされたネイティブページで変換が失敗する |
| 全面誤検出ガード | 検出枠がキャンバスの縦横とも過半を覆う「行」は無視(復元も除去もしない) | 写真全体を1行と誤検出→全面インペイントで背景破壊 |
| 修正台帳のリプレイ | 人間/エージェントの文字修正をfixes_ledger.jsonlに永続化し、変換のたびに合成前へ冪等リプレイ | フル再解析(バージョンアップ等)で手動修正が消え、同じタスクが再提示される |
| 認識不能テキストの保持 | 解決アドバンスが検出インク幅の55%未満かつ信頼度/相関が弱い行は画像のまま | 立体・メタリック題字の誤読テキストがレイアウトを破壊する |
| 低相関解のサイズ不信 | NCC<0.25の解はテンプレート由来サイズを信用せず検出枠高×0.88でクランプ | パネル発光・グロー混入で膨張した巨大文字が枠を突き破る |
| 極性リトライの拡大 | NCC<0.45で逆極性を再計測、+0.02以上良ければ採用 | 発光オーブ上の白文字が暗色で出力され背景と同化 |
| 除去の自己検査と再修復 | 修復後も元インク模様と相関が残りコントラストが高い領域を実測検出し、マスク膨張で2回目のLaMa | グレア上・強コントラスト文字のぼやけた残像が背景に残る |

### フォント戦略
- スキャン: システム+ユーザーフォントを fontTools で列挙(family名/weight/パス)。
- 同梱推奨(OFL): Noto Sans JP(和文)、Oswald / Roboto Condensed(欧文コンデンス)。
  `python fetch_fonts.py` でプロジェクト `fonts/` へダウンロード。
  インストールを促す(PPTX受け渡し先でも必要)。
- 候補から自動選択: 実測インク形状との照合スコア(幅比・密度)で決定論的に選ぶ。
