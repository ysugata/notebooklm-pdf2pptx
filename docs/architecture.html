notebooklm-pdf2pptx — Technical Anatomy

画像のスライドが、編集できるPPTXになるまで

NotebookLM (Gemini Notebook) が生成するスライドは、文字まで含めて1枚の画像です。notebooklm-pdf2pptxは、その画像から文字を「読み・測り・解き・消し」、デザインを保ったままPowerPointネイティブの編集可能テキストへ置き換えます。このページは、使われている全ての機能・技術・ツール・AIを図解します。

8段処理パイプライン
2つだけのAI (全てローカル)
±3px実測較正済みの文字配置
180秒で100ページ

全体パイプライン

1ページごとに8つの段階を通ります。各段の成果物はwork/pages/にキャッシュされ、同じ入力なら再実行をスキップします(レジューム)。

STAGE 1 — acquire

入力の分解

使用技術: PyMuPDF (fitz) + Pillow。PDFのページが「全面1枚の画像」で構成されている場合(NotebookLM出力の典型)、レンダリングし直さず埋め込み画像そのものをネイティブ解像度(1376×768)で抽出します。再サンプリングによる劣化ゼロで後段の計測精度が決まります。

  • 画像フォルダ入力にも対応(NotebookLMから画像で出力した場合)
  • アスペクト比が16:9から2%以上外れる資料は、スライドサイズ自体を元比率に合わせる
  • 全面画像でないページは高解像度レンダリングにフォールバック
STAGE 2 — ocr 機械学習

文字を読む

使用技術: RapidOCR 3.9.2 + ONNX Runtime(推論エンジン)。モデルは PP-OCRv6(PaddleOCR系、Apache-2.0)。検出はDBNet(文字領域をポリゴンで切り出す)、認識は50言語統一モデルです。すべてローカル推論で、ネットワーク不要。

認識の工夫

  • 認識前に2×Lanczos拡大(小さい文字の精度向上)
  • 行単位で検出+文字/単語ボックスと信頼度を取得
  • 信頼度の低い行はreport.jsonと注記画像で人に引き渡す
  • --ocr-model mediumで日本語精度88.2%→90.5%に切替可

読み取り後の決定論後処理

  • スペース復元: 文字間ギャップの統計外れ値を検出し、さらに画像上に本当に空白列が連続するかを検証してから挿入(検出ボックスの偽ギャップ対策)。単語ボックスが融合して届かないケース(camelCase・×等の記号境界)は、解決後にフォント送り幅から予測した位置の空白列を実測し、挿入で照合が改善する場合のみ採用する二段構え
  • 強調数字ランの分割: 「FY2027 15.0億円」のような大きな数字を、高さの段差検証つきで独立要素に切り出す
  • 丸記号の字形確定: 評価表の◎○●をOCRがラテン文字「O」と誤読するため、丸様文字のみの行はグリフ輪郭の入れ子構造(二重輪/単一輪+穴/塗り)を実測して正しい記号へ置換
  • 行端の混同字裁定: 装飾の波ダッシュ「〜」がカタカナ「ヘ」等に誤読された場合に備え、行頭・行末の混同字は代替字でテンプレートを描き直しNCC比較で確定
STAGE 3 — measure

文字を測る

使用技術: OpenCV + NumPy。行ごとに局所的な画像計測を行い、文字の「物理量」を数値化します。全て古典的画像処理で、閾値はどの資料にも共通です。

計測手法役割
インク抽出Otsu二値化 + bbox内部の少数派で極性決定。照合相関が弱い場合は逆極性で再計測し良い方を採用明るい帯の上の白文字などの極性誤りを自己修復
コア分離半値しきい値(背景とピーク輝度の中点)グロー(光彩)と字画本体を分離。ぼけに不変
文字の高さ行密度トリム(まばらな行を除外)照合レンダ側と同一規則で対称に比較
太さ距離変換のメディアン×2ウェイト(細字/太字)候補の絞り込み
色純色サンプリング: 背景から最も遠い上位30%画素縁の混色で白が灰色にくすむのを防止
色ラン分割文字セルごとの純色を計測し、輝度正規化クロマ距離+輝度比の切り替わりで行内を色ランに分割「初年度15億円の」のような部分強調を1行1色に潰さない
グラデーション上下1/3の色差(RGB距離≥28)金色グラデ文字などを2色グラデで再現
罫線の混入除去連結成分分析(幅85%超・扁平)帯・バーの縁の影を文字と誤認しない
背景の性質周囲リングの色分散 + ハロー率除去方式(フラット/グロー/テクスチャ)の判定
STAGE 4 — solve (精度の核)

文字を解く — テンプレート照合

「認識したテキストを、候補フォントで実際に描画して、元画像と重ね合わせる」のがこのツールの心臓部です。描画は Pillow (FreeType)、メトリクスは fontTools、照合は OpenCVの正規化相互相関 matchTemplate(TM_CCOEFF_NORMED) を使います。

探索と選択のルール(全て一般則)

  • サイズ: 初期推定の0.70〜1.12倍を1pxピッチで全探索(過大推定に強い非対称範囲)
  • 位置: マッチの許容変位はインク中心基準で±0.18em。グローで上端がずれても中心は安定し、隣の行への誤マッチも防ぐ
  • 字間(spc): 各サイズで幅が元画像と一致するよう解析的に決定。ただし可読性下限−0.08emより詰めない。+0.11emを超える広げは「インク幅の膨張」の疑いがあるため、自然字間のテンプレートも並行照合してNCCに裁定させる
  • フォント・ウェイト: ヒューリスティックスコア上位6候補+未登場ウェイト帯(細/中/太)の最良を必ず含め、最終判定は相関値で行う
  • 正則化: サイズ乖離・過大な字間・非ポータブルフォント・未収録グリフ(豆腐化)に軽いペナルティ。OCR検出枠の高さをサイズ上限プライアとして利用。小さい文字(20px未満)は僅差時に軽いウェイトを優先(JPEG圧縮による過剰bold防止)
  • スクリプト処理: 和文主体の行は和文候補、純欧文の行は欧文候補。和文文字や幾何記号(◎○●等)を1つでも含む混在行は両候補の和集合を土俵に乗せ、未収録グリフのペナルティに選ばせる。欧文主体の行はNFKC正規化で全角記号をASCII化(等幅フォントの未収録グリフ回避)

段落化 (STAGE 5 — group)

同スタイル・等ピッチで縦に並ぶ行を1つのテキストボックスへまとめ、行間は実測ピッチを固定行高(spcPts)で指定。整列(左/中央/右)は行端の揃い方の分散から自動判定し、ブロック内のフォント・サイズの揺れは最良相関の行に統一します。

STAGE 6 — remove 機械学習(適応)

文字を消す — 適応式3方式

文字を編集可能にするには、背景から元の文字を消す必要があります。背景の性質を計測して、3方式を自動で使い分けます。

before / after (LaMa inpainting)
GLOBAL PROJECT
  • デバイスは CUDA → MPS → CPU の順で自動選択。Windows+NVIDIAではbootstrapがCUDA版PyTorchを自動導入
  • --inpaint classic でLaMaを使わない完全古典モードにも切替可能
  • グロー検出は「背景より輝度+25以上の発光ハロー」のみ。PPTX側ではPowerPointネイティブの光彩効果として文字に再付与
STAGE 7 — compose

PPTXを組む

使用技術: python-pptx + lxml(OOXML/DrawingML直接注入)。PowerPointのレンダリング差を実測して選んだ「最も裏切られにくいXML表現」で書き出します。

書き出しているXML表現

  • a:spcPts — 全段落の行高固定
  • a:latin / a:ea / a:cs — 和欧フォント両指定
  • spc — 1/100pt単位の字間
  • a:gradFill — 文字のグラデーション塗り
  • a:glow — 光彩効果
  • kern="10000" — カーニング無効化(幅計算の決定性)
  • wrap="none" + noAutofit — 再レイアウト禁止

サイズと堅牢性

  • 座標は全てEMU(1/914400インチ)で厳密変換
  • 背景はJPEG化+python-pptxの同一画像dedupでファイル肥大を防止
  • rPr子要素をOOXMLスキーマ順に挿入(厳格なパーサでも壊れない)
  • ボックス幅に折返し余裕(wrap非対応レンダラ対策)

フォント戦略

  • ポータブル優先: Noto Sans JP / Oswald / Roboto Condensed / Roboto Mono(等幅) / Rounded Mplus 1c(丸ゴシック) / BIZ UDPGothic(全てOFLまたはWindows標準)を優先。どの環境でも同名で解決でき、fetch_fonts.py --installで導入できる
  • fontToolsでname・OS/2・hhea・cmapテーブルを解析し、PowerPointが解決できるバインディング名(例: Bold接尾辞の剥がし、非RIBBIはフルネーム)を導出
  • グリフ収録チェック: 選択フォントに無い文字(豆腐化)は候補ペナルティ+要確認レポートへ
  • 実機レンダラで較正済み(tools/calibrate.py): ベースライン誤差±3px以内
STAGE 8 — qa

自動検証

変換のたびに「元画像とどれだけ一致したか」を自動で数値化・可視化します。AIによる目視に頼らない検証ループです。

ツール内容
qa (組込み)解決値を同じフォントで自己レンダリングし、元画像とのSSIMと差分画像を出力
tools/render_quicklook.pyApple純正エンジン(QuickLook)でPPTXを実レンダリング(1ページずつ単一スライド化)
tools/compare.py元画像とレンダ結果の見開き比較シート
tools/review_sheet.py低信頼OCR行を元画像上に赤枠+認識文字列で注記(人の確認箇所を明示)
tools/measure_alignment.py要素単位のズレ(位置・幅・高さ)を自動計測し統計と最悪箇所を列挙
tools/smoke_test.pyPPTX構造検査(はみ出し・行間・フォント指定の欠落)
tools/calibrate.py既知位置のプローブPPTXを実レンダラで測定し、行レイアウト定数を較正

AIはどこに使われているか

機械学習は2箇所だけ。どちらもローカル推論で、クラウドAPI・生成AIには一切依存しません。同じ入力からは常に同じ出力が得られます。

コンポーネント種別モデル / 手法実行場所ライセンス

背景修復 (複雑背景のみ)MLLaMa (大域マスク画像修復)PyTorch / GPU可Apache-2.0
計測・照合・配置・色・字間決定論OpenCV / Pillow / fontTools / NCCCPU—

PPTX生成・検証決定論python-pptx / lxml / SSIMCPU—

かつて必要だった「AIによる手調整」(旧版では112要素を手作業で補正)は、STAGE 4のテンプレート照合が肩代わりしています。資料固有の座標・補正値はコードに存在しません。

スケーラビリティと性能

100ページ対応の設計

  • ページ毎に中間物をキャッシュ、入力+設定のハッシュでレジューム
  • メモリは常に1ページ分のみ(100ページでもピーク約1.2GB)
  • LaMaは対象ページを集めて1プロセス一括実行(モデルロード1回)
  • 同一背景画像はPPTX内で自動共有(ファイル肥大防止)

実測値

  • OCR+計測+照合: 2〜4秒/ページ (CPU)
  • 100ページ(classicモード): 180秒
  • LaMa: GPU(CUDA/MPS)で1〜3秒/ページ、CPUでは数十秒〜
  • 再現度 SSIM: 0.87〜0.95 (検証5ページ)
